# Versiones y releases

## El número

Tisma engine usa el [versionado semántico 2.0.0](https://semver.org/lang/es/): `MAYOR.MENOR.PARCHE`, con una etiqueta
de pre-release opcional (`0.6.0-alpha.1`).

- **Una sola fuente:** el archivo `VERSION`, en la raíz. CMake lo lee. El programa lo muestra en `--version` y lo
  escribe en la primera línea de cada G-code (`; generated by Tisma engine 0.6.0-alpha.1`). Nadie escribe el número
  en otro lado.
- **Antes de 1.0.0** (todo el desarrollo del plan):
  - **MENOR** sube con cada fase del plan o con un grupo grande de funciones nuevas. Puede cambiar los formatos (ajustes,
    caso de análisis, informe) y la línea de comandos; cada cambio así se anota en `CHANGELOG.md`, en «Cambiado» o
    «Quitado».
  - **PARCHE** sube solo con correcciones, sin funciones nuevas ni cambios de formato.
- **1.0.0** es la primera versión para producción. La decide el dueño. Desde ahí, un cambio incompatible sube MAYOR.

Hitos ya cumplidos, que no se publicaron por separado:

| Versión | Fase |
|---|---|
| 0.1.0 | F0, esqueleto |
| 0.2.0 | F1, corte por capas |
| 0.3.0 | F2, paredes de ancho variable |
| 0.4.0 | F3, superficies y relleno |
| 0.5.0 | F4, G-code |
| 0.6.0 | F5 (empezada), A1 y exportación verificada; primera publicada como 0.6.0-alpha.1 |

## Las etiquetas de pre-release

| Etiqueta | Cuándo | Dónde |
|---|---|---|
| `-alpha.N` | Una fase en curso: funciona, se puede probar, todavía faltan partes | rama `dev` |
| `-beta.N` | La fase está completa y se está validando (criterios del plan, pruebas reales) | rama `dev` |
| `-rc.N` | Candidata: lista para que el dueño la fusione en `main` | rama `dev` |
| ninguna | La fase fusionada en `main` por el dueño | rama `main` |

N empieza en 1 y sube con cada release de la misma versión y etiqueta.

## Cuándo hay release

Hay release cuando se junta un grupo de mejoras grandes o relevantes para quien usa el motor. Por ejemplo:
- una función nueva que se puede probar;
- un paso de fase cumplido;
- varias correcciones que cambian lo que sale.

No hace falta release por cada envío. Antes de publicar:
1. **Todo verde:** `tools/ci_linux.sh` pasa en la sesión y la CI de Windows pasa en GitHub para ese commit.
2. **Número:** `VERSION` tiene el número nuevo.
3. **Notas:** `CHANGELOG.md` tiene su sección `## [versión] - fecha`, con lo de «Sin publicar» movido ahí, y los
   enlaces del final actualizados.
4. **Comprobación:** `tools/release_notes.py --check` pasa (CTest lo corre).
5. **Etiqueta:** una etiqueta anotada `v<versión>` en ese commit, enviada a GitHub (`git push origin v<versión>`).

Con la etiqueta, el flujo `.github/workflows/release.yml`:
- compila y prueba en Windows y en Linux;
- empaqueta el programa con la licencia, el README, el registro de cambios y la documentación de uso;
- publica la release con las notas de su sección del CHANGELOG, marcada como pre-release si el número tiene etiqueta.

Si la etiqueta no coincide con `VERSION`, o el CHANGELOG no tiene la sección, el flujo falla antes de compilar.

## Los formatos tienen su propia versión

El motor cambia más seguido que sus formatos. Los formatos que leen otros programas llevan su propio número, que sube
solo cuando el formato cambia de manera incompatible:
- el informe de análisis (`"version": 1`);
- la estimación (`"version": 1`);
- los avisos del laminado (`"version": 1`).

Los nombres de los ajustes (`docs/CONFIG.md`) son estables. Si alguno cambia, se anuncia en el CHANGELOG.
